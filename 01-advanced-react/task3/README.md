# Задача 3. Срочный ввод и transition для дорогого списка

## Цель

Отделить срочный ввод от обновления дорогого списка.

## Что нужно сделать

1. Возьмите лабораторию урока 02 как базу: сохраните нагрузку в отдельных карточках и границу memo списка.
2. Реализуйте независимые text и listQuery: text обновляется срочно, listQuery — внутри startTransition. Покажите isPending.
3. Сравните обычный режим и transition при одинаковых данных и нагрузке; запишите наблюдения без обещания фиксированного ускорения.

## Требования к результату

- Управляемый input не обновляется внутри transition.
- После завершения списка виден последний запрос, в том числе после очистки.

## Запуск

```bash
cd 01-advanced-react/task3
npm install
npm run dev -- --host 127.0.0.1
```

## Наблюдения

1. База из урока

   В `Results.tsx` перенесён базовый поиск: 240 элементов, тяжёлый цикл в каждой `CourseCard`, `Results` обёрнут в `memo`. Нагрузка и данные одни и те же для обоих режимов, режим переключается радиокнопками.

2. text и listQuery

   `text` хранит значение поля, `setText` вызывается сразу, вне transition. `listQuery` уходит в `Results`: в режиме transition он обновляется внутри `startTransition`, в обычном режиме сразу вместе с `text`. Пока transition не закончился, рядом с запросом видно «обновляется…» (`isPending`), а список полупрозрачный. Для сравнения в `useLayoutEffect` пишутся логи `[input]` и `[list]`: сколько мс прошло от ввода до commit поля и списка.

3. Сравнение режимов

   Проверка одинаковая: по одному символу ввести «c», стереть, снова «c» и так несколько раз. И «c», и пустой запрос показывают все 240 карточек, так что каждый раз полная нагрузка.

   В обычном режиме `[input]` и `[list]` приходят вместе, примерно через 38–44 мс на каждое нажатие. Поле ввода ждёт, пока перерисуется весь список.

   В режиме transition `[input]` 0–1 мс на каждое нажатие, поле обновляется сразу. Промежуточные списки не коммитятся: когда приходит новый символ, React бросает незаконченный рендер. Список для последнего запроса появился через 83 мс после последнего нажатия, после очистки поля через 109 мс.

   Сам список от этого быстрее не стал, до финального списка даже прошло больше времени, потому что рендер идёт частями и начинается заново. transition не ускоряет работу, он только даёт вводу приоритет. Цифры получены в dev-режиме со StrictMode и на другой машине будут другими.

4. Требования

   В `startTransition` попадает только `setListQuery`, поэтому управляемый input внутри transition не обновляется. После того как список закончил рендер, виден последний запрос, в том числе после очистки: «Запрос списка: «»», все 240 элементов, индикатор пропадает.

Самопроверка: `npm run build` проходит без ошибок.
